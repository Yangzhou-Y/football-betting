## 一、合约模块化拆分（5 个 commit，`fix/contracts-dividing` 分支）

### 1.1 背景

PRD 发起人反馈原有合约文件 `FootballBetting.sol`（879 行）过大，建议从结构化角度拆分。经评估，该文件承载了 5 类职责：ERC-20 接口、枚举/结构体/事件/错误定义、状态变量与修饰器、赛事管理逻辑、投注与结算逻辑、查询函数。

### 1.2 拆分方案（`74bb2ad`）

采用 **抽象合约 + 多重继承** 模式，确保最终合约 ABI 完全不变（前端和测试零改动）。

**拆分后文件结构**：

| 文件 | 职责 | 行数 |
|------|------|------|
| `IERC20.sol` | ERC-20 最小接口（transferFrom/transfer/balanceOf） | 31 |
| `FootballBettingTypes.sol` | 2 个枚举 + 2 个结构体 + 13 个事件 + 33 个自定义错误 | 141 |
| `FootballBettingBase.sol` | 状态变量 + 构造器 + 3 个修饰器 + 6 个 internal helper | 166 |
| `FootballBettingAdmin.sol` | 赛事生命周期 + 暂停 + 管理员管理（recordResult 在此） | 203 |
| `FootballBettingBet.sol` | placeBet + cancelBet（USDT transferFrom 模式） | 103 |
| `FootballBettingSettle.sol` | claimReward + withdrawFee | 57 |
| `FootballBettingQuery.sol` | 6 个 view 函数（getMatch/getAllMatches/getUserBet 等） | 102 |
| `FootballBetting.sol` | 多重继承聚合，~55 行，对外唯一入口 | 55 |

**继承链**：所有功能模块继承 `FootballBettingBase`（→ `FootballBettingTypes`），最终 `FootballBetting` 多重继承全部 4 个功能模块，C3 线性化自动解析。

**验证结果**：
- 编译成功（`npx hardhat compile`）
- 65 个测试全部通过
- Gas 消耗与拆分前完全一致（Solidity 继承在编译时解析，零运行时开销）

## 二、前端视觉主题升级（1 个 commit，`main` 分支）

### 2.1 足球场草坪主题背景（`3da927e`）

**问题**：原有背景仅一行纯色渐变 `linear-gradient(180deg, #f0f7f0 → #f8fafc → #f4f8f0)`，视觉上与"足球"产品无任何主题关联，缺乏辨识度。

**方案**：纯 CSS 多层 gradient 叠加 + SVG 球场元素装饰，零图片请求。

**CSS 背景 6 层结构**（`globals.css` body）：

| 层序 | 层次 | CSS 技术 | 视觉效果 |
|------|------|---------|---------|
| ① | 草坪底色 | `linear-gradient` | 从球场绿 `#c8e6c0` 渐变到边线外 `#f0f4ef` |
| ② | 割草机条纹 | `repeating-linear-gradient(0deg, ...)` | 60px 间隔水平浅深交替 |
| ③ | 斜向草纹 | 双 `repeating-linear-gradient`（47° + -33°） | 草叶方向变化颗粒感 |
| ④ | 径向聚光 | `radial-gradient(ellipse at 50% 30%, ...)` | 中心区域高亮，边缘略暗 |
| ⑤ | 顶部灯光 | `linear-gradient(175deg, rgba(255,255,255,0.5) → transparent)` | 聚光灯从上方打下效果 |
| ⑥ | 整体固定 | `background-attachment: fixed` | 滚动时背景不移动 |

**球场线装饰**（`WorldCupBackground.tsx` 新增）：

- 边线框（`border-[40px] sm:border-[60px]`，10% 不透明度）
- 中线 + 中圈 + 开球点
- 四个角球弧（`rounded-br-full` / `rounded-bl-full` 等组合）
- 已有的球门、奖杯、浮动足球保留不变

**性能**：全部 CSS gradient + SVG inline，无图片加载，首屏 0 额外请求。

## 三、移动端体验修复（3 个 commit，`main` 分支）

### 3.1 底部 Tab Bar 定位异常（`e5637d1`）

**问题**：移动端底部 Tab Bar 出现在页面顶部，遮住了导航栏控件。

**根因**：Tab Bar 的 `<div className="sm:hidden fixed bottom-0">` 嵌套在 `<nav className="sticky top-0">` 内部。`sticky` 定位创建了新的 CSS 包含块，导致 `fixed bottom-0` 在部分移动浏览器上无法正确定位到视口底部。

**修复**：将 Tab Bar 从 `<nav>` 内部移出，作为 `<nav>` 的同级元素，用 `<></>` Fragment 包裹两者。`fixed bottom-0` 现在相对于视口定位，不受 sticky 包含块影响。

**涉及文件**：`frontend/src/components/layout/Navbar.tsx`（+48/-46）

### 3.2 移动端横向滚动问题（`7bf486b` → `20cb73d`）

**问题**：背景草坪条纹和球场线装饰导致移动端页面可以左右滑动，赛事和我的竞猜页面尤为严重。

**修复方案（两层加固）**：

1. `globals.css` body 添加 `overflow-x: hidden` + `max-width: 100vw`
2. `layout.tsx` html 元素添加 `overflow-x-hidden`
3. `WorldCupBackground.tsx` 将 `overflow-hidden` 改为 inline style `style={{ overflow: "hidden" }}`，避免 Tailwind 类被 body 的 overflow 覆盖

**涉及文件**：`frontend/src/app/globals.css`（+2），`frontend/src/app/layout.tsx`（+1/-1），`frontend/src/components/layout/WorldCupBackground.tsx`（+1/-1）

## 七、经验总结

1. **合约拆分的继承模式选择**：多重继承 + 抽象合约的方式保证了 ABI 完全不变，前端和测试零改动。如果用 Library 模式，一些 internal 函数需要改为 public 并通过 `using for` 调用，会增加合约调用开销。继承在 Solidity 中是编译时内联的，零运行时成本。

2. **CSS 包含块是 fixed 定位的常见陷阱**：`fixed` 通常相对于视口定位，但如果祖先元素有 `transform`、`filter`、`perspective`、`will-change` 或 `sticky`（部分浏览器实现），就会创建新的包含块，导致 `fixed` 元素被"困"在祖先内。将 fixed 元素移到 DOM 树的顶层是最稳妥的解法。

3. **移端横向滚动的根本原因通常是某个子元素超出视口宽度**：`overflow-x: hidden` 只是兜底方案。在本项目中，球场线装饰的 `border-[40px] sm:border-[60px]` 使用了 `absolute inset-0` 且位于 `fixed inset-0` 容器内，理论上不应该溢出，但某些移动浏览器对 `border` 的盒模型计算不同。`max-width: 100vw` 在 `overflow-x: hidden` 之外提供了额外保障。

4. **纯 CSS 背景的视效上限**：使用 6 层 CSS gradient + inline SVG 可以做出相当精细的视觉效果，且零带宽、无限缩放。但复杂 gradient（特别是多层 repeating-linear-gradient 交织）在低端移动设备上可能有微小的渲染性能影响，值得关注。当前方案中所有 gradient 的色块间距都在 30-60px 级别，属于轻量级渲染。

5. **合约拆分前应充分评估 ABI 影响**：本项目中所有 public/external 函数签名、事件、状态变量布局、构造器参数均在拆前后完全一致——这是选择继承模式的关键约束。如果未来有人要在拆分后的文件中加入新的 public 变量，必须注意 Solidity 的存储布局通常是继承链底层合约的变量排在前面。
